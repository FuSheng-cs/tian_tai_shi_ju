# 创新论证｜自由语言怎样成为游戏规则

> 2026-10-29 · AIC 独立项目架构与交互机制说明。

## 创作命题与技术命题

创作命题是：面对困境中的人，仔细斟酌说出的每一句话。技术命题是：怎样让玩家自己组织的语言进入可反馈、可结算、有终点的游戏规则？

本作以“自由输入 → 角色回应 → 结构化语义判定 → 程序结算 → 可感知反馈”共同回答这两个问题。语言是玩家操作，十句是资源约束，状态是反馈，结局是收束。

## 机制与表达相互证明

| 设计 | 游戏中的作用 | 对创作命题的贡献 | 实现依据 |
| --- | --- | --- | --- |
| 自由语言输入 | 玩家自己组织话语，输入随上下文变化 | 让开口成为自己的选择 | GameView.vue、gameStore.ts |
| 最多十句话 | 每次发送消耗一次机会，信任不返还句数 | 让玩家衡量当下最值得说什么 | gameContract.ts、game_contract.go、gameStore.ts |
| 角色与独立裁判 | 角色生成自然对白，裁判返回结构化状态 | 让回应的含义进入反馈，而非只得到另一段文字 | service.go 的 Chat / EvaluateTurn |
| 程序守门 | 归一化字段、结算信任、校验结局条件 | 维持十句与结局边界，使互动能够收束 | 前后端契约和低信任拦截 |
| 对白、状态与预制 CG | 呈现戒备、动摇、落泪、离开等变化 | 让玩家观察回应，再决定下一句 | gameContract.ts、GameView.vue |
| 后日谈 | 安全离开后延续上下文 | 让人物生活延续，避免把一次对话当作全部 | ChatAfterStoryView.vue、SaveSystem.ts、路由守卫 |

以上源码位于 `legacy_vue/src/` 与 `backend/llm/`，详见[技术说明](technical_overview.md)。

## 一轮交互的实际顺序

1. 前端记录本句并消耗 1 次机会，发送历史、剩余机会、信任与状态。
2. 后端角色调用生成艾的自然对白。
3. 独立裁判结合本句、历史、角色回复与当前状态输出 `emotion`、`ai_state`、`trust_delta`、`pressure_delta`、`ending_type`、`confidence`。
4. 程序校验结构和枚举，先扣压力造成的信任损耗，再加信任增量，上限 15。
5. 安全离开同时要求本轮结算信任达到 15 和有效叙事判定；低信任离开会被拦截。满分或哭泣不自动成功。
6. 前端显示对白、机会和状态对应画面；十句耗尽且没有有效安全结局时，收束为拒绝离开。

裁判判断上下文中的表达，双调用分别负责自然对白和结构化过程反馈；它们可使用同一服务商或模型。

## 从模型条件反推游戏形态

- **交互规模与成本**：十句约束单局主线回合数，提示、摘要、后日谈与重试纳入调用预算。
- **响应节奏**：单场景、短对白、沉默和观察构成交互节拍，双调用按“生成→评价”顺序推进。
- **发散控制**：固定天台、人物设定、短回复要求、结构化裁判和程序门槛共同约束叙事路径。
- **数字媒体呈现**：CG、对白节奏、机会刻度与后日谈把状态变化转成可见反馈；打字机负责本地显示节奏。

## 创新落地链路

展示时把一条实际输入、角色回复、裁判 JSON、程序结算和界面变化放在同一条证据链上。低信任拦截结局由对应测试展示程序边界；Mock 测试覆盖契约与程序行为，真实模型记录覆盖语义与体验。

可复核位置：`legacy_vue/tests/gameStore.test.ts`、`legacy_vue/tests/gameContract.test.ts`、`backend/llm/trust_gate_test.go`、`backend/llm/game_contract_test.go`。

## 评估重点

本作评估玩家是否能够读懂具体回应、识别沟通动作、理解信任与压力反馈，并在有限机会中调整下一句话。测试重点覆盖 Prompt 契约、裁判字段、程序结算、复盘展示和安全边界。
